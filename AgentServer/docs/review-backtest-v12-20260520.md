### 收益下降原因分析
收益从34.25%降到23.86%是消除两个偏差的正常结果：
1. **P0-1**: cost_basis从模拟价→含滑点实际成交价，止损基线更准确
2. **P0-2**: 买入价系数0.7→0.8，更接近实盘(0.7在涨幅1.05%处买入，0.8在2.4%处)
3. **回撤改善0.77%** 是最重要的指标改善——修正后风控更精确

## 发现的问题

### P0 (影响回测正确性)

#### P0-1: 调仓日买入价记录为策略模拟价而非实际成交价
- **位置**: `_rebalance()` 买入逻辑(第3832行附近)
- **问题**: `self._cost_basis[ts_code] = price` 中的 `price` 是 `_get_buy_price_for_stock()` 返回的模拟价
  (如半路追涨的 `open*(1+min_rise*0.7)`)，而非实际成交价(含滑点的 `buy_price_adj`)
- **影响**: 止损/止盈价格基于模拟价计算，而非实际成本，导致触发阈值偏差
  - 例: 半路追涨open=10元, 模拟价=10×1.021=10.21, 实际成本=10.21×1.002=10.23
  - 止损价偏差: 10.21×0.95=9.70 vs 10.23×0.95=9.72, 差0.02元(每笔)
- **修复**: cost_basis 应记录 `buy_price_adj` (含滑点的实际成交价)

#### P0-2: 半路追涨买入价模拟系数过保守
- **位置**: `_get_buy_price_for_stock()` 第3158行
- **问题**: 买入价 = `open × (1 + min_rise_pct × 0.7)`，系数0.7过于保守
  - min_rise_pct=3%时，买入价=open×1.021，即假设在涨1.05%时买入
  - 但实际上3%涨幅确认时股价已经在3%位置，0.7系数相当于假设在1.05%就买入
  - 这导致cost_basis偏低，回测收益虚高(买入更便宜)
- **影响**: 虽然消除未来函数是正确的，但0.7系数让买入价过于保守，回测收益偏高
  - 实盘无法在1.05%时就确认3%涨幅信号
- **修复**: 系数从0.7调整为0.9，更接近实盘场景（看到2.7%涨幅时确认3%信号并买入）

#### P0-3: 跌停翘板筛选条件缺少 limit_down_open_amount 翘板金额过滤
- **位置**: `_build_strategy_filter_conditions()` 跌停翘板分支(第3374行)
- **问题**: 策略参数有 `min_qiao_amount` 但筛选条件中未使用
  - 日线回测中 `limit_down_open_amount` 因子存在，但条件列表中缺失
  - 导致无翘板金额过滤，选出大量低质量翘板股
- **影响**: 跌停翘板策略26笔交易中可能包含资金不足的弱翘板
- **修复**: 添加 `limit_down_open_amount >= min_qiao_amount` 条件

### P1 (影响回测质量/性能)

#### P1-1: 非调仓日 `_process_non_rebalance_day` 重复查询价格
- **位置**: 第1806行
- **问题**: 调仓日 `_process_rebalance_day` 已获取prices并存入last_prices，
  但非调仓日又独立查询一次MongoDB获取价格
- **影响**: 每个交易日多1次MongoDB查询(约3秒)，累计大量耗时
- **修复**: 复用last_prices缓存，仅在股票列表变化时查询增量

#### P1-2: run_state解包/重包模式代码冗余
- **位置**: `_process_rebalance_day` 和 `_process_non_rebalance_day`
- **问题**: 每个early return都需要手动解包15+个变量、重新打包15+个变量到run_state
  - 每个return点约30行重复代码，共7个return点=210行纯样板代码
- **影响**: 代码膨胀、维护困难、容易漏改
- **修复**: 使用 `run_state.update({...})` 替代逐字段赋值

#### P1-3: 板块集中度过滤使用当日pct_chg排序
- **位置**: 第1520行
- **问题**: 用当日涨跌幅(pct_chg)作为行业内的选股评分
  - pct_chg是未来函数(收盘后才知道)，实盘无法在选股时使用
  - 应使用开盘可观测的因子(如量比、开盘涨幅)排序
- **影响**: 选股结果含前瞻偏差，回测偏乐观
- **修复**: 改用 `volume_ratio` 或 `intraday_open_rise_pct` 排序

#### P1-4: 特殊时期过滤器缺少2025年春节配置
- **位置**: `special_period_filter.py`
- **问题**: DEFAULT_CONFIG只有2026年春节，没有2025年春节
  - 2025年春节(1月28日-2月4日)是重要长假期，回测2025年数据时不会降仓
- **影响**: 2025年初回测结果可能偏乐观
- **修复**: 添加2025年春节配置

#### P1-5: universe._get_tradable_stocks 查询无日期索引优化
- **位置**: universe.py 第121行
- **问题**: `{"trade_date": int(trade_date)}` 查询stock_daily_ak_full全量字段
  - 每天查询一次约3秒，但只需要ts_code和close
- **修复**: 已有projection，确认索引即可

### P2 (优化/体验)

#### P2-1: 因子引擎 daily_basic 合并使用逐行赋值(慢)
- **位置**: factor_engine.py 第112-124行
- **问题**: 用for循环逐行 `result.loc[idx, col] = db_df.loc[idx, col]` 合并
  - 比pandas原生 `update()` 或 `combine_first()` 慢100倍
- **修复**: 改用 `result.set_index('ts_code').update(db_df)` 或 `combine_first()`

#### P2-2: 调仓日强制空仓卖出价用open而非VWAP
- **位置**: 第1138行
- **问题**: 强制空仓用open价卖出，但极端行情下开盘价可能极低
  - 实际上投资者看到极端行情可能在开盘到收盘之间逐步卖出
  - 用VWAP(均价)更合理
- **修复**: 当有vwap数据时优先使用

#### P2-3: _rebalance 中的 max_hold_days 用日历天数*1.5近似
- **位置**: 第3555行
- **问题**: `calendar_days > max_hold_days * 1.5` 不精确
  - 法定假后首日: 买入周五→持有3日历天(1交易日)→max_hold=3, 3>3*1.5=4.5不触发
  - 但买入周一→持有5日历天(5交易日)→max_hold=3, 5>4.5触发
  - 同样3个交易日，一个触发一个不触发
- **修复**: 应该用交易日差而非日历天数，或在run_state中传入交易日列表

## 修复优先级
1. P0-1 (cost_basis记录错误) — 影响所有止损止盈判断
2. P0-2 (买入价系数过保守) — 影响回测真实性
3. P0-3 (翘板金额过滤缺失) — 影响策略质量
4. P1-2 (run_state样板代码) — 提高可维护性
5. P1-3 (板块过滤未来函数) — 消除前瞻偏差
6. P1-4 (2025春节缺失) — 数据完整性
7. P2-1 (daily_basic合并性能) — 加速
8. P2-3 (max_hold_days精度) — 精确性
